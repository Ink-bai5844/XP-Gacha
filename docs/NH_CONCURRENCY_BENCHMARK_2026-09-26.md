# NH 断点续采与动态并发测试（2026-09-26）

> **2026-09-27 完整性勘误：** 后续核查发现，测试时的 NH HTML 选择器不兼容新增样式类，且只检查标题就计为信息成功。下文新增 CSV 数量和吞吐实际包含缺少其他元数据的记录，不能当作完整信息的采集成绩；原请求状态统计作为历史观察保留。解析、完整性校验和旧行回补已修复，完整元数据吞吐及策略排序需要重新验证，以下速度建议不应视为修复后结论。

## 结论与使用建议

**本次当前网络的最佳候选是 2 并发；需要自动调节时，建议在 NH 采集页面选择“分档探索”，并发上限仍保持 30，其余截图参数不变。** 它从上限启动，本次经过六档探索后选择了 2；不应把 2 硬编码成所有网络、所有时间的最优值。兼容原有调用，未传策略时仍保留 `stable` 默认值；需显式选择新策略。

反向对照 `30 → 2 → 30` 每组均运行 240 秒，前后两组 30 并发剔除预热后的速度分别为 18.289、18.290 条/分钟；2 并发为 21.433 条/分钟，**本次点估计约高 17.2%**。若按完整四分钟、不剔除预热计算，三组分别新增 73、80、67 条，候选比两组 30 的平均新增数高约 14.3%。两个口径方向相同，但仍只有一组候选复测，不能当作长期稳定提速幅度或统计显著性证明。

三种动态策略的整轮测试并没有显示明显提速：大步初版为 17.686、分档探索为 17.380 条/分钟，分档探索包含低效档和校准成本。它的价值在于发现当前更合适的档位，**不是一启动就快，也不意味着能突破平台配额**。短任务不一定值得完整探索；长任务可让其持续比较有效成功吞吐。

请求数是附带观察，不参与策略评分：固定 2 的四分钟发送 151 次请求、收到 71 次 429；固定 30 前后分别发送 1,343 / 1,316 次请求、收到 1,270 / 1,249 次 429。选择低档的依据仍是成功数，而不是仅仅让失败率好看。

## 测试范围

## 如何计量

- 主要指标是实际写入 CSV 的新增详情数除以实际耗时，不是 HTTP 请求数、失败率或控制台行数。
- 初始化与备份不计入爬取时间；剔除最初 30 秒；计时截止后协作停止，收尾写入不进入吞吐排名，但成果照常保留。
- 新控制器换档后也弃用一个完整 30 秒过渡窗口。评分将有效成功数及真实耗时汇总，避免把 `0 / 20 / 0` 的周期性成功错误取中位数得到 0。
- 前两组历史对照使用 `metricVersion: 1`，计数来自进度缓存；后续使用 `metricVersion: 2` 直接读取已持久化 CSV 计数。前两组只作探索参考，不据此声称几个百分点的显著提升。
- 每组独立备份 CSV、断点并核对 SHA256；输出锁防止多个新版采集任务同时写相同文件。
- 实验顺序会受到站点配额相位、网络、待补条目差异影响。单次短测不能证明全局最优；固定档位复测用于检查方向是否重复。

## 实现变更

1. 保留原 `stable` 相邻探测，新增 `adaptive-step` 大步探索/缩步回退及 `bandit` 几何分档、折扣记忆和定期复测。所有策略从输入上限启动且不超上限，不用失败比例作为优化目标。自适应最终版另限制下探步长不超过当前档的一半、上探不超过翻倍，避免初版 `15→1` 跨过有效区域；上表初版实测不冒充最终版复测。
2. NH 使用每工作线程独立的持久连接，减少重复握手；线程池退出后释放连接。保留关闭复用的对照开关。
3. 同一站点共享服务端明确要求的冷却时间；重试加入少量随机错峰，停止等待仍可取消。
4. 前端与终端均可选策略，切换策略不改变断点标识。进度补充策略、信息和图片完成数；兼容旧任务上报。
5. 新增安全基准工具：默认只展示计划，显式 `--run` 才访问网络；支持固定并发对照、定时停止、Ctrl+C 安全收尾、备份及源码哈希追溯。

## 复现实验

在项目根目录的 PowerShell 中运行：

```powershell
# 只查看计划，不访问网络、不更改采集数据
.\.venv\Scripts\python.exe -X utf8 tools\benchmark_collection.py --strategy bandit

# 使用本次参数和同一断点，实测 15 分钟后安全停止
.\.venv\Scripts\python.exe -X utf8 tools\benchmark_collection.py --run --strategy bandit --duration 900

# 固定档位对照；30 是上限，4 是本组实际并发
.\.venv\Scripts\python.exe -X utf8 tools\benchmark_collection.py --run --fixed-concurrency 4 --workers 30 --duration 240

# 正式续采，不设测试计时器；恢复同一份断点
.\.venv\Scripts\python.exe -X utf8 -m data_get.collector nh-online --max-pages 700 --workers 30 --strategy bandit --request-attempts 3 --timeout 30 --retry-backoff 5 --max-rounds 0
```

不要同时从前端和终端启动写入同一份 CSV / 断点的任务。锁是协作式保护，无法阻止旧版程序或外部编辑器修改文件。

## 离线模型边界

`tools/simulate_collection_concurrency.py --include-quota` 会实际调用三种控制器，在合成吞吐曲线上模拟运行，不发送网络请求。它用于验证上限、启动假高吞吐过滤和探索逻辑，不用于预测 NH 的真实速度。

模型表明没有一种策略在所有场景都最快：相邻探测在稳定平台上探索损耗较小，却容易在高并发降效场景卡住；大步自适应更快覆盖不同档位；分档策略初扫成本高，环境变化时可能受旧档位评分影响。周期配额模型中三者成功数近似相同。这些结论不能作为 NH 提速百分比。

即使剔除启动窗，60–90 秒档位评分也可能受站点周期影响。`10/8/10` 等窗口可以汇总成有意义的吞吐，但还不能把仅差 5% 的两个档位认定为真实优劣。建议长期任务观察多个周期，重要结论用固定档位反向复测；不要仅看一次内部评分。
